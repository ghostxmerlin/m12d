# m12d 阶段 2：按需人脸识别 设计

> 上位设计：`2026-11-09-m12-vision-design.md`，本文细化其中的 §5"身份"、§6"请求和回复"、§10 第 2 项。两者冲突时以本文为准。标【用户定】的是用户的决定，标【我的决定】的是 Claude 的取舍，用户可以推翻。

## 1 意图

- StackChan 要知道"眼前这个人是谁"。M12 只负责把结果准确、快速地**报告**出来；什么时候问、拿结果做什么，由 StackChan 安排。【用户定，2026-11-10："你报告就行，主机会安排"】
- 原厂人脸识别每帧都做身份比对，只有 2–3 fps，用户已否决。我们只在被问到时才算一次。阶段 1/1b 的人脸检测、人形检测和年龄性别照常运行。
- 第一个被学习、也用于验收的人脸是用户本人。【用户定】

## 2 目标、非目标、反目标

**目标**
- 四条新指令：学习、识别、删除、列出。走统一指令集（§6），串口和 TCP 完全相同。
- 识别请求延迟不超过 300 ms，从请求到达到回复发出算起（上位设计 §2）。
- 人脸库掉电不损坏：写到一半断电，重启后要么是旧库，要么是新库。
- 用户本人在正脸、左右转头约 30°、低头、笑、约 1 米、暗光下都能被认出。别人不能被认成用户。

**非目标**
- 不在每帧自动识别，也不在新面孔出现时自动识别。
- 不做活体检测和防照片攻击。
- 不做人脸库的导入、导出和串口传输（上位设计 §12）。

**反目标**（即使功能能用，出现以下情况也算失败）
- 把别人认成用户（误认）。宁可说"不认识"，也不能认错。
- 识别请求让检测帧率明显下降，或者让检测行中断超过 0.5 s。
- 人脸特征被提交进公开仓库。人脸库是生物特征数据，只留在设备上。

## 3 已有条件

- 模型：原厂 `mobilefacenet.{param,bin}`，在设备的 `/home/m5stack/payload/models/` 下，`research/` 里也有一份副本。
  - 输入是 112×112 RGB，用五点对齐。输出 128 维特征。原厂的阈值是相似度 > 0.5。
- 对齐：`src/vision/align.{h,cpp}` 已经实现了原厂 arcface 的五点相似变换（模板 x 加 8）。阶段 3 的单测验证过它。
- 每张脸已经有跟踪 id（`FaceTracker`），检测行输出 `"id"`。StackChan 可以用这个 id 指定要识别哪张脸。
- 人脸检测在 192×144 上做，五点坐标换算到 320×240 后，从 320×240 的 RGB 上对齐裁剪。原厂识别也在 320×240 上对齐。
- 离线数据：`tests/data/faceid/` 有用户本人的 32 帧，包括正脸、左右转、抬头、低头、笑、约 1 m、暗光。背景里有同事，部分帧有同事正脸，可以当作"非本人"样本。`tests/data/set/` 里还有阶段 1 的 28 帧。这些都不提交。

## 4 指令（统一指令集）

字段名照上位设计 §6 的惯例。【我的决定】

**选哪张脸**：所有指令都可以带 `"face":<跟踪 id>`。不带时用当前画面里最大的那张脸。指定的 id 当前不在画面里时，回复 `noface`。
- 这里偏离了上位设计"第几张脸"的说法：StackChan 在检测行里看到的是 id，用 id 指定更不容易错。

1. **学习** `{"id":1,"do":"learn","name":"<名字>"}`
   - 从被选中的这张脸上，在约 1.5 s 内跨帧采 **5 个样本**，两个样本至少相隔 150 ms，并且要求是同一个跟踪 id。
   - 采到 5 个样本后，存进这个名字下面，回复 `{"id":1,"ok":true,"name":"…","samples":<该名字的样本总数>,"f":<最后一帧>}`。
   - 3 s 内没采满 5 个（人走开或转身）时，回复 `{"ok":false,"err":"noface"}`，这次采的样本一个都不存。
   - 同一个名字可以多次学习，样本会累积，每个名字最多 **20** 个，超出时丢掉最旧的。这样可以在不同光线和角度下分几次学。
   - 名字：UTF-8，1–32 字节，不能含控制字符。库里最多 **16** 个名字，满了回复 `full`（新增错误码）。
   - 防误学：新学的样本与**另一个名字**的相似度高于识别阈值时，回复 `{"ok":false,"err":"conflict","name":"<那个名字>"}`，不存。
2. **识别** `{"id":2,"do":"who"}`
   - 对被选中的脸取**当前帧**，提取一个特征，与库中每个样本算余弦相似度。每个名字取其样本中的最大值，再在名字之间取最大值。
   - 回复 `{"id":2,"ok":true,"f":<帧号>,"face":<跟踪 id>,"name":"…"|null,"sim":0.73}`。最高相似度低于阈值时，`name` 为 `null`，`sim` 仍然给出。
   - 库为空时回复 `name:null, sim:0`，不算错误。
3. **删除** `{"id":3,"do":"forget","name":"…"}`：回复 `{"ok":true,"name":"…"}`；名字不存在时回复 `badarg`。
4. **列出** `{"id":4,"do":"faces"}`：回复 `{"ok":true,"faces":[{"name":"…","samples":N},…]}`。

**识别结果写回检测行**【我的决定】
- `who` 认出某个跟踪 id、或者对它 `learn` 成功之后，只要这个 id 还在被跟踪，检测行里这张脸就带上 `"name":"…"`。
- 这一步不增加任何计算，StackChan 不必反复去问。不做自动识别。
- 写回的名字在以下情况清除，宁可清掉也不能让名字挂错脸：
  - 之后对同一个 id 的 `who` 返回了别的名字：替换成新名字。
  - 之后对同一个 id 的 `who` 返回 `null`：清除。`who` 返回 `null` 也是 `ok:true`，只是"不认识"。
  - `forget` 删除了这个名字：所有挂着这个名字的跟踪都清除。
  - 这个 id 离开画面超过 1 s，被跟踪器遗忘。
  - 这张脸的框与另一张脸的框有重叠：两张脸都清除。
    - 原因：跟踪器只按重叠匹配，两个人交错走过时可能互换 id。

## 5 执行方式【我的决定】

- 识别相关的计算放在**检测线程**里，在两帧之间执行，不另开线程。
  - 设备只有 2 个核，检测已经用了 2 个线程，再开一个线程只会互相抢。
  - 这和年龄性别的做法一致，结果也是确定的。
- 请求排队：IO 线程把 learn / who 请求放进一个**最多 4 条**的队列，满了回复 `busy`。
  - 检测线程每帧最多做一次 mobilefacenet 推理。
  - **`who` 优先**：有 `who` 在等时，这一帧先给最早的 `who`；没有 `who` 在等时，才给正在采样的 `learn` 采一个样本。这样 `learn` 采样期间，`who` 仍然能在 300 ms 内回复。
  - 只用一个时钟：每个请求从**入队**起计时，期限都是 3 s。
    - `who` 到期还没做（例如一直没有可用的脸），回复 `timeout`。
    - `learn` 到期还没采满 5 个样本：如果到期时画面里没有被选中的那张脸，回复 `noface`，否则回复 `timeout`。两种情况都不存任何样本。
    - `who` 收到时如果画面里没有脸（或者没有指定的那个 id），立即回复 `noface`，不进队列。
- `forget` 和 `faces` 不需要推理，直接在检测线程的下一帧处理。人脸库只由检测线程读写，所以不需要加锁。
- 温控暂停（tier 3）期间，learn / who 回复 `hot`。
- 检测关闭（`cfg det:false`，待机）期间，learn / who 立即回复 `standby`（新增错误码），不排队。StackChan 要识别时，先 `cfg det:true`，等检测行里出现脸以后再问。
- 预算：mobilefacenet 在设备上的单次耗时实现时要量出。原厂资料没有直接数字；按模型规模估计在 15–40 ms。
  - `who` 的总延迟大约是：等一帧（不超过约 65 ms）+ 对齐和推理。这远低于 300 ms 的要求。
  - learn 的 5 个样本分散在 5 帧里做，每帧只多一次推理。

## 6 人脸库

- 文件：应用目录下的 `data/faces.bin`，也就是设备上的 `/home/m5stack/m12d/data/faces.bin`。【我的决定】
- 格式：小端二进制。
  - 头部：魔数 `M12F`、版本号 1、名字数。
  - 每个名字：名字长度、名字、样本数、样本数 × 128 个 float32（已做 L2 归一化）。
  - 文件末尾附 CRC32。
- 写入：
  1. 先写 `faces.bin.tmp`，然后 `fsync`。
  2. 再 `rename` 成 `faces.bin`，然后对目录 `fsync`。
  - 只有 learn 和 forget 会触发写入。
- 读取：启动时加载。下面几种情况都记日志，然后以**空库**启动，并把坏文件改名为 `faces.bad.<时间>` 留作检查，不覆盖、不删除：
  - 文件不存在；
  - 魔数、版本或 CRC 不对；
  - 文件长度和内容不符。
- 隐私：`data/` 不在仓库里，`.gitignore` 加上 `data/`。测试用的特征在测试运行时现算，不落盘到仓库。

## 7 阈值【我的决定，由数据确定】

- 先用离线数据定阈值，再在设备上验证：
  1. 用户的正脸样本（`id_front`）当作"学习"样本。
  2. 其余姿态当作"本人"测试集。
  3. 同事的脸当作"非本人"测试集。
  4. 画出两组相似度的分布。
- 选阈值的原则：先保证非本人的最高相似度低于阈值，并且留出余量；在这个前提下尽量让本人的检出率高。原厂用的是 0.5，作为起点。
- **达标线**【我的决定】：
  - 非本人误认必须为 0。
  - 本人在正脸、左右约 30°、约 1 m 这几种情况下，按帧计的识别率不低于 90%。
  - 抬头、低头、笑、暗光只报告，不作为门槛。
  - 学习可以分多次进行（例如正脸一次、转头一次），离线评估时就按实际的学习方式来。
- 如果在 320×240 上对齐、达不到达标线：
  - 先试从 640×480 原始帧对齐裁剪。上位设计 §5 已经把这件事留给阶段 2 评估。
  - 再达不到，就停下来向用户报告数据，不硬调阈值。
- 局限：非本人样本只有少数几位同事的几帧，阈值的可信度有限。报告里要说明这一点，以后可以随时用 `cfg` 调整（见下）。
- `cfg` 新增 `id_th`（0.3–0.9），用来在运行时调整识别阈值，不写入人脸库。

## 8 验收

- **A 离线**
  - 主机上，ncnn 版 mobilefacenet 与原厂流程（原厂 arcface 代码在主机上重新编译）对同一个对齐裁剪的输出一致，余弦相似度 ≥ 0.999。
  - 用 §7 的数据：本人各姿态的识别率逐项报告；**非本人误认为 0**。
- **B 指令**：learn / who / forget / faces 的全部错误分支都有单测，包括 `noface`、`busy`、`timeout`、`full`、`conflict`、`badarg`、`hot`，以及人脸库的损坏和恢复。串口和 TCP 的命令脚本一致。
- **C 设备**（需要用户配合，约 5 分钟）
  1. 用户用自己的名字学习一次。随后在正脸、转头、约 1 m 处各 `who` 几次，记录识别率和延迟。延迟的 p95 应不超过 300 ms。
  2. 连续每秒 `who` 一次、持续 60 s，检测帧率下降不超过 10%。
  3. 掉电测试：learn 回复之后立刻拔掉 M12 的电源，重启后 `faces` 里仍有这个名字。这一步需要用户动手。
  4. 删除用户的名字后，`who` 回复 `null`。

## 9 留给实现者决定的事项

- mobilefacenet 的输入输出节点名、是否要做归一化：以原厂 `arcface.cpp` 为准。
- 学习时跨帧采样的具体时间间隔，只要满足 §4 的约束即可。
- 识别请求队列的数据结构，以及它与 `Dispatcher` 的对接方式。目前 `Dispatcher` 是同步回复，learn / who 需要延迟回复。
