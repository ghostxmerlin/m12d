## 1 意图

M12（UnitV2-M12）是 StackChan 的视觉协处理器。StackChan 通过 Grove 串口告诉它"现在要什么"，M12 负责**快速、可靠地执行**，并且**不能过热**。

至于 StackChan 什么时候调用、拿到结果后做什么，都是 StackChan 的事，不在本项目范围内。【用户定】

原厂固件的问题：每个功能是一个独立程序，切换功能就要重启进程，且一次只能运行一个功能。原厂人脸识别每帧都做身份识别，只有 2–3 fps，用户已否决。原厂框架还有空转线程、无锁队列等缺陷。我们要用一个自己的常驻程序替代它。

## 2 目标、非目标、反目标

**目标**
1. 一个常驻进程。启动时载入全部模型，运行中不切换模型、不切换进程。【用户定】
2. 人脸检测每帧持续运行，帧率至少达到原厂 face_detector 的水平（实测约 6.8 fps，见 §3）。这个帧率只要求在温控"正常"档位下达到。温度升高后按 §7 降帧是允许的。【用户定】
3. 按需请求的延迟目标【我的决定】：
   - 身份识别、属性：不超过 300ms
   - 物体、房间：不超过 1 秒
   - 请求执行期间，检测帧率最多下降一半
4. 以下能力按需调用，用请求到达时的当前帧计算：【用户定】
   - 人脸身份识别
   - 人物属性（年龄、性别）
   - 场景识别：猫、常见物体、房间
5. 温度高时自动降级：先降检测帧率，再暂停按需任务，温度回落后自动恢复。永远不触发原厂 95°C 保护。【用户定】
6. 可靠性：
   - 崩溃后自动重启，并留下退出原因。
   - 摄像头异常时自动恢复。
   - 请求有上限，每个请求都有超时。
7. 所有推理都在 M12 上运行。【用户定，来自交接文档】

**非目标**
- StackChan 端的调用逻辑和业务流程。
- 投入使用后的视频预览和网页界面。开发调试工具可以有，但不属于交付物。
- 替换内核、U-Boot 或整个 rootfs。
- 在 Mac 上做推理。Mac 只用来编译、转换模型、做数值对照和查看结果。

**反目标：出现以下任何一条，即使功能正常也算失败**
- 触发原厂 95°C 保护。触发后设备降到 400MHz，只能重启恢复。
- 进程无声退出，没留下任何痕迹。原厂程序就有这个问题，见 §3。
- 把设备锁死在无法访问的状态，或者破坏回到原厂状态的路径。
- 在运行时关闭 Wi-Fi。这会让网络栈卡死，见 §3。

## 3 已测得的设备事实（2026-11-09，本机实测）

**硬件与系统**
- 系统为 Buildroot 2020.02.8，内核 4.9.84。
- 系统库：glibc 2.30，libstdc++.so.6.0.28（对应 GCC 10）。
- OpenCV 4.4 在 `/lib`，另有 3.4.9 在 `/usr/lib`，链接时不要混用。
- CPU 为双核 Cortex-A7，支持 NEON 和 vfpv4。
  - 开机时 `S05initled` 把调频策略固定为 performance，即锁在 1.4GHz。
  - 可选频率：400、600、800、1000、1100、1200、1400MHz。
  - 可选调频策略：userspace、powersave、ondemand、performance。
- 内存：MemTotal 114MB。原厂服务全开时 MemAvailable 约 75MB。
  - `server_core.py` 约占 15MB 常驻内存，`check_thermal.py` 约 4MB。

**摄像头**
- UVC 设备 0bda:5842，节点 `/dev/video0`，只有 root 能访问。
- YUYV 格式支持 320×240 和 640×480，最高 30fps；也支持 160×120、352×288、800×600 等。
- MJPG 格式最高 1080p 30fps。
- 原厂框架用 OpenCV 以 MJPG 格式采集 640×480，缩小到 320×240 后检测。

**串口**
- Grove 口为 `/dev/ttyS1`，原厂用 115200 波特率。
- `/dev/ttyS0` 是内核控制台（在 cmdline 里），上面有 getty，没有引出。

**USB 调试口**
- 板上有一颗 USB 转以太网硬件芯片（CoreChips "USB 10/100 LAN"），接在 SoC 的 EMAC 上，设备端网卡是 `eth0`，驱动 Sstar-emac。
- 系统没有 UDC，所以**不可能做 USB CDC 串口**。
- 设备地址 10.254.239.1，DHCP 由 dnsmasq 在 eth0/br0 上提供。

**Wi-Fi**
- 芯片为 RTL8188FU（USB 0bda:f179），驱动是可卸载模块 `8188fu`。GPIO14 控制 Wi-Fi 供电，开机时为输出 0（上电）。
- **在运行时关闭 Wi-Fi 会导致整个网络栈卡死。** `killall hostapd` 之后，hostapd 卡在内核里退不出来，USB 网络随之失效，只能断电重启。共复现 2 次。
- **现在的做法：开机就不启动 Wi-Fi。**
  - `/etc/init.d/S90wifi-conf` 已被修改：最多等 8 秒让 SD 卡挂载，然后如果存在 `/media/sdcard/m12-nowifi`，就跳过 Wi-Fi。
  - 原文件备份在 `/media/sdcard/m12test/S90wifi-conf.orig`。
  - 必须等待的原因：SD 卡由 mdev 在后台挂载，不等就会和 Wi-Fi 启动发生竞争。
  - 没有 br0 时，`S95ip-conf` 会把 10.254.239.1 配到 eth0，同时也配到 wlan1。USB 的 SSH 和 DHCP 都正常。
  - 已知瑕疵：wlan1 也拿到了同一个地址，以后要处理。
- 效果：开机后 5–10 分钟的空闲温度，Wi-Fi 开着为 71.7°C，不启动为 63.7°C，**约低 8°C**。环境温度没有控制。
- GPIO14 断电没有测试过。

**原厂温控 `/etc/thermal/check_thermal.py`**
- 每 60 秒读一次 `/sys/devices/system/cpu/cpufreq/temp_out`。
- 达到 95°C 时：调频策略改为 powersave，杀掉命令行里含 `./bin/`、`server.py`、`server_core.py` 的进程，再开一个过热提示网页。不会自动恢复。
- 温度也可以从 `/sys/class/mstar/msys/TEMP_R` 读，格式为 "Temperature NN"，两个读数一致。

**原厂启动与停止的陷阱**
- `S85runpayload stop` 和 `S110thermal stop` 用的都是 `killall -9 python3`，会把温控程序一起杀掉。**禁止使用**。停原厂服务时只按 PID 结束 `server.py` 和 `server_core.py`。
- 设备上的 `/bin/sh` 是 zsh。普通用户 m5stack 不能写 `/dev/null`。没有 `pkill`。设备上的 scp/sftp 不可用，文件传输用 ssh 加 cat 或 base64。

**原厂程序基线（Wi-Fi 关闭）**
- `face_detector` 每帧约 147ms，即约 6.8 fps，CPU 约 96%，常驻内存约 22MB，6 个线程。
- 温度：直接运行 5 分钟，从 67°C 升到 77°C，仍在上升，没有到稳态。用户此前测过 Wi-Fi 开着长时间运行约 90°C。
- **偶发无声退出**：第一次通过原厂服务运行，27 秒后进程消失，没有错误输出，内核也没有记录。之后 1 次直接运行 5 分钟、1 次通过服务运行 2 分钟，都没有复现。原因未知，怀疑是框架里的无锁队列（见下）。
- 子进程死后，`server_core` 进入坏状态：之后每次切换都在 `os.kill` 处报错，只能重启服务。

**原厂框架的缺陷**（`upstream/UnitV2Framework`，已核对源码）
- `sleep(0.001)` 实际等于 `sleep(0)`，导致 `PIPESendThread`、`SendingThread`、`getMat` 空转。
- `queue_sending_pipe` 被多个线程同时写、同时读，完全没有加锁。`queue_output_mat` 的锁也被注释掉了。
- `loadModel` 不检查加载失败。另一个三参数的重载没有返回值。
- `merge_feature` 的参数按值传入，融合结果写不回原特征。

**模型**
- 设备上的模型文件，与 `research/2026-11-09-app-readiness` 里从恢复包提取的版本，SHA256 一致。
- 设备目录 `/home/m5stack/payload/models` 下有：
  - mnet.25-opt（RetinaFace，约 0.85MB）
  - mobilefacenet（约 4.1MB）
  - nanodet_m（约 1.9MB）
  - shufflenet_v2_x0.5-opt（约 5.5MB）
  - yolo-fastest（约 1.2MB）
  - 以及 OCR 等模型

## 4 约束

- 只能使用原厂 Linux 和驱动。不修改 libc 和系统 OpenCV，也不替换系统库。
- **编译产物必须能在设备现有的库上运行**：
  - 不能依赖 GLIBC 2.30 之后的符号版本。
  - libstdc++ 不能超过 GLIBCXX 3.4.28。
  - 链接设备的 OpenCV 4.4。
- 开发期间不改动原厂 payload 目录。程序放在独立目录，随时可以回到原厂状态。
- 开发时始终保留原厂 `check_thermal.py`，作为最后一道保险。
- 内存：所有模型常驻，加上运行时开销，要放进约 75–90MB 可用内存里，并留出余量。投入使用时停掉原厂 Python 服务，可以多出约 15–20MB。
- Grove 串口 115200 约等于 11KB/s。持续输出的检测结果必须紧凑。

## 5 整体架构

```
摄像头 /dev/video0 (YUYV)
   │ 采集线程：只保留最新一帧（单槽缓冲，加锁＋条件变量）
   ▼
检测线程 ── RetinaFace 每帧 ──► 检测结果 ──► 推送队列 ──► IO 线程 ──► /dev/ttyS1 + TCP 客户端
   │            （同时保存"最新帧＋最新人脸框"快照）
   ▼
按需工作线程 ◄── 请求队列（有上限） ◄── 分发器 ◄── IO 线程 ◄── /dev/ttyS1 + TCP 客户端
   ├─ 身份识别：对齐 112×112 → MobileFaceNet → 与人脸库比对
   ├─ 年龄/性别：同一张对齐人脸 → age_gender 模型
   ├─ 物体/猫：整帧 → NanoDet
   └─ 房间：整帧 → ShuffleNetV2 特征 → 与房间库比对
温控监视（主进程内）── 读温度、调档位 ──► 检测帧率上限、是否接受按需任务
```

**进程与线程**【我的决定】
- 一个进程，四类线程：采集、检测、按需工作、IO。IO 线程用一个 poll 循环同时管串口和 TCP 的收发，见 §6。温控放在主循环里。
- 线程之间全部用有锁的队列或条件变量通信，禁止空转等待。
- 设计目标是空闲时 CPU 接近 0。

**核心分配**【我的决定，待实测】
- 检测线程和按需线程各用 ncnn 单线程，分别绑定一个核，这样按需任务运行时不会拖垮检测帧率。
- 实现时要对比"检测独占 2 线程，按需任务时临时让出"的方案，选帧率和延迟更好的那个。【留给实现】

**采集**【我的决定，待实测】
- 默认用 V4L2 YUYV 采集 **320×240、10fps**，直接用于检测。【用户定，2026-11-09 实测后】
  - 以 640×480 YUYV 采集时，内核开销会把推理拖慢 15–30ms，检测帧率追不上原厂。
  - 320×240 模式的视野与 640×480 相同，是整体缩放，不是裁切。
  - 原厂识别也在 320×240 上对齐。
  - 数据见 `results/2026-11-09-capture-experiments.md`。
  - 识别如果需要更高分辨率，阶段 2 再评估按需临时切换到 640×480。
- **近距离模式**【用户定，2026-11-09】：
  - 用户说明了使用距离：日常玩耍在 1 米以内；外出等场景会超过 1.5 米。
  - 检测输入默认 192×144，摄像头 30fps。
  - 实测 17.95 fps，原厂 6.95 fps。
  - 约 100px 的近脸全部检出，约 50px 的脸 11/12 检出，见 `results/2026-11-09-input-size-sweep.md`。
  - `--det-size 320x240` 是与原厂一致的路径，B 层对比就是在这个路径上做的。
- **远距离：人形检测**【用户定，阶段 1b】：
  - 模型用 Yolo-Fastest 160×160，设备已有，实测约 37ms/次。NanoDet-m 160 需要 73ms，留给阶段 4。
  - 调度：有脸时每帧做人脸检测，每 5 帧做一次人形检测；无脸时两者交替。
  - 融合：脸的中心落在人形框上部，就认为是同一个人；检测行增加 `person` 列表，标明配对的脸。原有字段不变。
  - 先补采 1.5、2.5、3.5 米站立的帧和空房间的帧，测检出率和误检率（例如挂着衣服的椅子）。
- 如果采集和转换的开销明显，检测路径可以改用 320×240 采集。这样会牺牲识别所用人脸的分辨率，需要用数据决定。
- 不使用 MJPG，避免每帧在 CPU 上解码。
- 采集可以用 OpenCV VideoCapture 加 FOURCC=YUYV，也可以直接用 V4L2 mmap。【留给实现】

**模型**（全部启动时加载，加载失败就明确报错并退出，由守护进程记录）
- 人脸检测：mnet.25-opt，与原厂相同。
- 身份：mobilefacenet，128 维特征，余弦相似度，与原厂相同的五点对齐。
- 年龄/性别：`research/2026-11-09-age-gender/age_gender.{param,bin}`
  - 输入 RGB 1×3×112×112。
  - 归一化已经包含在图里，不能重复做。
  - 输出 fc1 共 202 维：前 2 维取 argmax 得性别，后 200 维按 100 对分别取 argmax 后求和得年龄。
  - 性别标签的含义需要核对。
- 物体和猫：nanodet_m，COCO 80 类，其中包含 cat。
- 房间：shufflenet_v2_x0.5-opt 提取特征（原厂"在线分类器"的做法），与已学习的房间样本做余弦最近邻。
- 内存如果实测不够，最少用到的模型改为首次使用时加载、之后保留。实现时要量出各模型的常驻增量。【我的决定】

**持久数据**
- 人脸库和房间库保存在应用目录的 `data/` 下。
- 写入采用"先写临时文件，再改名替换"的方式，防止断电损坏。
- 可以从 SD 卡导入、导出。【我的决定】

## 6 统一指令集：串口与网络共用（M12 提供的能力，StackChan 如何使用不在范围内）

**传输**【用户定：网络和串口统一指令集，2026-11-09】
- 串口：`/dev/ttyS1`，115200 8N1。
- 网络：TCP 端口 5555，最多 2 个客户端。设备上有网络接口时就监听，比如开发时的 USB 网络；`--tcp-port 0` 可以关闭。
- 两种传输层用的协议完全相同：一行一条 JSON，以 `\n` 结尾，请求最长 512 字节。传输层只负责收发字节。行的切分、解析、分发和回复都是同一份代码。
- 不兼容原厂的串口命令（例如 `{"function":"Face Detector"}`）。【用户定】

**三种消息，靠字段区分**
- 请求：`{"id":7,"do":"<命令>",...参数}`。
- 回复：`{"id":7,"ok":true,...}` 或 `{"id":7,"ok":false,"err":"<错误码>"}`。回复只发回请求来源的那个通道。
- 推送：不带 `id`，包括检测行（字段与原厂一致，见下）和心跳行 `{"hb":{...}}`。推送发给所有订阅了的通道。串口默认订阅，TCP 客户端在连接时也默认订阅，可以用 `cfg` 关闭。

**阶段 1 的命令**：`ping`、`ver`、`status`、`cfg`，以及调试用的 `snap`（把最新帧和它的检测结果一起存成文件，供 Mac 叠图检查）。`cfg` 可以设置检测开关（待机）、是否带五点坐标、`max_faces`、`fps_cap`，以及本通道是否接收推送。不带参数时只读取配置。回复里总是带上修改后的完整配置。后续阶段的命令都套用同一个格式。

**通用错误码**：`badjson`（不是合法 JSON，回复里 id 为 -1）、`unknown`（未知命令）、`badarg`、`toolong`（行超长，这一行整行丢弃）、`busy`、`hot`、`timeout`、`noface`、`nomodel`。

下面的字段名是示意，实现时可以调整，但下列语义必须具备。【我的决定】

**持续推送（M12 → StackChan）**
- 检测结果，每帧一条，内容尽量紧凑：
  - 帧号、时间戳
  - 每张脸的框（基于 640×480 坐标）、置信度、五点坐标
  - 是否开启五点坐标、最多推送几张脸，都可以配置
- 心跳，约每 1–2 秒一条：温度、温控档位、当前检测帧率、CPU 频率、空闲内存、运行时长、上次重启原因。

**请求和回复（StackChan → M12 → StackChan）**
- 请求带编号，例如 `{"id":7,"do":"who"}`。回复带同一编号，包含结果或错误码。
- 计算基于请求到达时的最新帧，回复里给出所用帧号，方便和检测结果对应。
- 支持的请求：
  - 身份识别：识别当前画面中的人脸。可以指定第几张脸，默认最大的那张。
  - 人物属性：年龄和性别，人脸选择方式同上。
  - 物体：物体列表，包括类别、置信度和框。
  - 房间：最可能的房间名和相似度。
  - 学习人脸、删除人脸、列出人脸。
  - 学习房间：在当前位置采样，可以多次累积。删除房间、列出房间。
  - 配置：检测开关（进入待机）、推送内容、温控阈值等。
  - 打开 Wi-Fi：调试用。运行时启动 hostapd 是否安全**尚未验证**，见 §9。
- 错误码至少包括：忙（队列满）、过热暂停、超时、没有人脸、模型不可用、参数错误。
- 请求队列上限和每个请求的超时都可以配置。【我的决定：默认队列 4 条，超时 3 秒】

## 7 温控

**第一层：主程序内部**【用户定：降级方式；我的决定：具体数值，可以配置】
- 每秒读一次温度，档位升降带 3°C 回差。
- 档位：
  - 正常：低于 80°C，检测不限帧率。
  - 一档：达到 80°C，检测帧率上限降低，例如 4 fps。
  - 二档：达到 85°C，暂停按需任务（回复"过热暂停"），检测帧率降到约 2 fps。
  - 三档：达到 90°C，停止检测，进入待机，只发心跳。
- CPU 频率不再锁死在 1.4GHz。实现时测出不同频率下的帧率和温度曲线，再决定默认频率，以及是否在执行按需任务时临时升频。【留给实现】

**第二层：独立看门狗**【我的决定】
- 一个很小的 C 程序，与主程序分开运行，每 2 秒读一次温度。
- 达到 93°C 时：调频策略设为 powersave，结束主程序，写日志。温度降到安全线以下后，交给守护进程按策略恢复。
- 开发期间与原厂 `check_thermal.py` 并存。看门狗验证可靠之后，才从投入使用的开机流程里去掉原厂温控。
- 主程序的可执行文件以 `./bin/m12d` 的形式启动，这样原厂温控在 95°C 时也能杀掉它，作为第三道保险。

## 8 可靠性

- **守护进程**：负责拉起 m12d，记录每次退出的退出码和信号，崩溃后带退避地重启。连续多次崩溃后进入安全待机，只发心跳并报告故障。
- **持久日志**：写到 SD 卡，或者应用目录下的轮转日志。重启后可以查看，包括崩溃时的最后上下文。
- **摄像头**：读帧失败或超时就重新打开设备，并在心跳里报告。
- **模型加载失败**：明确报错，不能静默地带着空模型继续推理。
- **长时间运行测试**：见 §10 阶段 5。

## 9 部署、开发与投入使用

- **应用目录**：设备上的 `/home/m5stack/m12d/`，包含 bin、models、data、log。不碰 `/home/m5stack/payload`。
- **开发期间**：
  - Wi-Fi 保持关闭，即保留 SD 卡上的 `m12-nowifi`。
  - 通过 USB 网络用 SSH 部署和查看。
  - 运行 m12d 之前，按 PID 停掉 `server.py` 和 `server_core.py`，以释放摄像头和 ttyS1。
  - 原厂温控一直保留。重启设备就回到原厂状态。
- **调试可见性和测试**：Mac 通过 USB 网络连 TCP 5555（§6），收到的推送和回复与串口上完全相同，所以不接串口也能看到全部内容。
- **验证统一性**：同一份命令脚本分别经 TCP 和串口执行，回复必须逐字一致。串口这一路先用 pty 模拟，之后用 3.3V USB-TTL 线（只接 GND/TX/RX，不接 VCC）在真实的 ttyS1 上再跑一遍。
- **不做网页预览**【用户定】：检测数据足够用来画框就可以。调试时由 Mac 脚本把框画到采集的图片上。
- **投入使用**【我的决定】：
  - 增加一个开机脚本，存在启用标记时启动 m12d 的守护进程和看门狗，并让原厂 `S85runpayload` 跳过。没有标记时完全按原厂行为启动。
  - 关闭方法：通过 USB SSH 删除标记后重启。
- **运行时打开 Wi-Fi**：
  - 已知运行时**关闭**会卡死；运行时**启动**还没有测过。
  - 在验证之前，打开 Wi-Fi 只能做成"写入标记，下次重启生效"。
- **备用急救通道**（可选）：调试模式下在 Grove 串口上开 getty，需要 3.3V USB-TTL 线或者用 StackChan 转接。它和投入使用时的串口协议互斥，只在急救时使用。

## 10 构建环境与开发顺序

**构建环境**【我的决定】
- 在 Mac 上用 arm64 Linux Docker 容器编译。编译器是 ARM 官方 gcc-arm-10.2-2020.11 的 aarch64 主机版（目标 arm-none-linux-gnueabihf）。
  - 要先确认这个下载确实存在。如果不存在，退回到 x86_64 主机版加模拟运行，或者其他能满足 §4 版本约束的编译器。
- **sysroot**：从设备拷贝 `/lib` 和 `/usr/lib` 中需要的库。OpenCV 4.4.0 的头文件从对应版本的源码中取。
- **ncnn**：用 Tencent/ncnn 提交 6afc736225de2f1b193292e31ca6242d138463d4（2021-02-22，与原厂头文件版本 1.0.20210222 一致）编译静态库。开启 OpenMP 和 NEON，关闭 Vulkan。
- 每次编译后，检查产物需要的 GLIBC 和GLIBCXX 符号版本不超过 §4 的上限。
- 编译命令和环境写成脚本，从零可以重复执行。

**开发顺序与每阶段验收**【用户定：顺序；我的决定：验收标准】

每个阶段分别报告四件事：编译通过、部署成功、功能通过、性能和温度数据。

阶段 0–1 的验收分成四层【用户与我共同确认，2026-11-09】：

0. **构建环境（A 层）**
   - 全静态测试程序在 M12 上运行成功，`readelf -d` 没有 NEEDED 条目。
   - 同一个输入张量交给 mnet.25，主机和设备的 ncnn 输出在浮点误差内一致。
   - 单帧推理耗时不高于原厂，原厂约 147ms/帧。
1. **复刻原厂人脸检测**
   - **B 层：检测正确性**，离线测试，结果可重复。
     - 先用 M12 采一组约 20 帧的 YUYV 固定图片，覆盖：没人、单人近距离、单人远距离、侧脸、多人、逆光。
     - 参照物：在容器里用主机的 OpenCV 编译原厂 `face_detector.cpp` 的推理和后处理，作为金标准。
     - 原厂的预处理是 MJPEG 解码，再用 `INTER_AREA` 缩小一半。我们用 YUYV 做 2×2 平均，数学上和 INTER_AREA 等价。
     - B1 核心一致：同一个 RGB 输入交给两边的检测核心。人脸数一致，坐标差不超过 0.5px，prob 差不超过 0.001。
     - B2 端到端：原厂流程（OpenCV YUYV→BGR，加 INTER_AREA）和我们的流程（yuyv_to_rgb_half）分别处理同一帧。人脸数一致，坐标差不超过 2px（按 640×480 计），prob 差不超过 0.02。
   - **C 层：功能**
     - 检测行的字段与原厂一致。
     - 统一指令集（§6）经 TCP 和串口执行，回复逐字一致：先用 pty，再用真实 USB-TTL。
     - 用收到的数据能把框画对，Mac 脚本叠图后由用户确认。
   - **D 层：运行**
     - Wi-Fi 关闭，三组各跑 5 分钟：原厂 face_detector、m12d、m12d 限到原厂同帧率。【用户定：测试先不用太长】
     - 指标：帧率不低于原厂；CPU 和温度低于原厂；全程不崩溃，RSS 不增长。
     - 长时间测试推迟到阶段 5。
   - 本阶段就要带上最基本的温控中止（90°C 停止）。
1b. **远距离人形检测与融合**（2026-11-09 新增，见 §5）
   - **已实现（2026-11-10）**：方案 ①，即 160 检测加 320 复核新目标。见 `results/2026-11-10-person-detection.md`、`results/2026-11-10-phase1b.md`。
   - 先实验：远距离检出率和误检率。
   - 再实现：调度和融合。
   - 指标：近距离人脸帧率不明显下降；1.5–4 米站立的人能检出。
2. **加入按需人脸识别**
   - 学习、识别、删除三个命令可用。
   - 量出：识别请求的延迟；识别期间检测帧率掉了多少；人脸库掉电后是否完好。
3. **加入人物属性**
   - 先在 Mac 上用原 MXNet 模型做参考，比对 ncnn 转换版的输出，确认数值一致（允许浮点误差）。
   - 再在设备上运行，量出延迟。
   - 用实际人脸检查结果是否合理。不能把"能输出一个数字"当作准确性通过。
4. **加入场景识别**
   - 物体和猫（NanoDet）、房间的学习和识别。
   - 量出：全部模型常驻时的内存峰值，以及各按需请求的延迟。
5. **完善为可投入使用的程序**
   - 分档温控、频率策略、看门狗、守护进程、开机集成、完整串口协议。
   - 长时间运行测试【我的决定：至少 4 小时】：持续检测，并周期性发送混合的按需请求。
   - 记录温度曲线、是否有崩溃、内存是否稳定。

## 12 补充决定（审阅后）

- **装入 StackChan 后怎么访问**【用户定】：
  - 装入后 M12 的 USB-C 口不接线，Wi-Fi 也关闭。需要调试或恢复时，拆机接 USB 是可以接受的。
  - 因此，通过串口做急救、导出日志、导出人脸库都不是必需的，可以以后再加。
  - 持久日志必须留在设备上（SD 卡或应用目录），拆机接上 USB 后能读到。
- **温度验收条件**【用户定】：
  - 开发和验收都先在当前裸机、USB 供电的条件下进行。
  - §7 的阈值和 CPU 频率策略，等实测数据出来后再定稿，现在的数值只是初始值。
  - 装进 StackChan 外壳、由 Grove 供电时的温度，以后另行测试，再据此调整阈值。
- **准确性由谁判断**【我的决定】：
  - 由用户用自己的脸、房间和猫做现场检查。
  - 年龄/性别额外与 MXNet 参考输出做数值比对。
  - 人脸识别必须达标，才能进入下一阶段。属性和场景识别结果偏弱时，只报告、不阻塞，后续再决定是否换模型。
- **阶段 1 的温度对比方式**【我的决定】：
  - 在相同条件下比较：Wi-Fi 关闭，开机后空闲状态起步，同样运行时长。
  - 指标：自有程序在不低于原厂帧率时，温度和 CPU 都应更低。
  - 另外测一组"把帧率限制到相同值"的对照，用来区分"更省"和"跑得更快"两种效果。
